## [0.9.2] - 2026-09-03

A patch release, and a large one: 55 pull requests from twelve contributors, most of them closing gaps in how buffa bounds untrusted input. 0.9.0 introduced the element-memory budget for the binary decoder; an audit of everything downstream of that decoder found the same fail-open shape repeated — the view and lazy-view entry points, the reflective decoder's packed scalars and enums, the textproto parser, extension records, nested unknown groups, descriptor-pool construction, and serialization of nested `google.protobuf.Any` — and each is now bounded. That includes the [CVE-2026-55407](https://github.com/anthropics/buffa/security/advisories/GHSA-f9qc-qg88-7pq5) follow-up reported in #357, where the extension-merge path gave every wire record its own full allowance. The two entries under *Security* are the stack overflow in reflective `Any` serialization and the map-entry parser differential between view and owned decoding. If your service decodes protobuf from the network, this is the release to take.

*Regenerate your code with a version-matched `buffa-codegen`.* Several fixes live on the generated path: `decode_view` now attaches the element budget, the view decoders merge split map values the way the owned decoder does, `to_dynamic` no longer rejects large messages the process built itself, generated enums carry `#[allow(non_camel_case_types)]`, and generated code reaches `core::fmt` and `serde` through absolute paths so a proto package named `core` or `serde` compiles. `buffa-build` users pick these up on the next build; `protoc-gen-buffa` and `buf generate` users must reinstall the plugin and regenerate — code generated by 0.9.1 still builds and runs against this runtime and gets every runtime-side fix, but keeps the old view decoders until it is regenerated.

The API is additive and MSRV is unchanged at 1.75; the migration surface is behavioural. Every hardening entry turns input that was previously unbounded into a limit error, and beyond those, five changes tighten what ordinary use could previously rely on, each called out in its own entry: the textproto parser applies an element budget by default, so a very large checked-in fixture can now fail to parse until the bound is raised; `DynamicMessage` charges packed scalars, so a reflective decode of a columnar payload above roughly half a million elements needs `with_element_memory_limit` raised; `DescriptorPool` rejects descriptor sets that reuse a reserved name or number, place a field in the 19000–19999 band, start an open enum at a non-zero value, or alias enum values without `allow_alias` — `protoc` never emits those, so only hand-built sets are affected; `PartialEq for DynamicMessage` compares unknown fields, so two messages that differ only in unknown content no longer compare equal; and the ProtoJSON `FieldMask` helpers now round-trip a leading underscore and reject malformed path components on both codecs. One addition can break a build rather than a decode: `buffa-types` gains `google::protobuf::Option`, which shadows the prelude `Option` in any module that glob-imports `google::protobuf::*`.

Beyond the hardening: `SharedCorpusContext` and `shared_descriptor_pool` cut codegen time and duplicated descriptor bytes for workspaces that generate one crate per package; `DynamicMessage::try_from_message` is a fallible bridge from a generated message; `buffa-types` now ships the complete well-known set, so googleapis compiles; `exclude_package` drops packages from a `buffa-build` run; the plugin gains `unbox_oneof` and `shared_descriptor_pool` options; and `SizeCache` panic sites are gated on `debug_assertions`, shrinking generated `compute_size`.

### Added

- **`CodeGenConfig::shared_descriptor_pool` emits the reflection descriptor set once at the module-tree root instead of once per package** (#311). When enabled, per-package `__buffa::reflect` modules delegate to a single shared `__buffa_fds` module; every consumer path (`pkg::descriptor_pool()`, `pkg::FILE_DESCRIPTOR_SET_BYTES`) keeps resolving as an alias, and all packages observe one `DescriptorPool`. Adds the `encode_descriptor_set`, `shared_descriptor_root_module`, `FdsEmbedding`, and `CodeGenConfig::reflect_feature_gate` surface that front-ends use to emit the shared module.

- **`shared_descriptor_pool=true` plugin option** on `protoc-gen-buffa` and `protoc-gen-buffa-packaging` (#370) — enables the shared descriptor pool (see `CodeGenConfig::shared_descriptor_pool`) on the plugin path. Set it on both plugins (same name on both, like `exclude_package`). Rejected together with feature overrides, feature-gating, or `file_per_package`, which the plugin path cannot support.

- **`buffa_build::Config::shared_descriptor_pool` enables the shared descriptor pool from `build.rs`** (#369). The descriptor set is written once as a binary sidecar next to the generated tree and `include_bytes!`-d by the shared `__buffa_fds` module, removing both the per-package duplication and the byte-literal source expansion. Requires reflection and `.include_file(...)`. With a checked-in `out_dir`, commit the emitted `*.descriptor_set.binpb` sidecar alongside the generated `.rs`.

- **`DynamicMessage::decode_with_options` and `merge_with_options` decode under caller-supplied limits** (#341), mirroring `DescriptorPool::decode_with_options`.

- **`TextDecoder::with_element_memory_limit` and `buffa::text::decode_from_str_with_element_memory_limit` raise the textproto parser bound above the default** (#344), reported past the limit as the new `ParseErrorKind::ElementMemoryLimitExceeded` variant.

- **A defaulted `SingularCodec::decode_one_ctx` lets repeated extension elements share one decode budget** (#345). Existing implementations need no change; the default forwards to `decode_one`, which is correct for any codec with a fixed per-record cost. A codec whose value can materialize an unbounded subtree must override it.

- **`buffa_descriptor::MAX_SYMBOL_LEN` and the `PoolError::NameTooLong` variant** (#347). `PoolError` is `#[non_exhaustive]`, so the variant is additive.

- **`generate_with_diagnostics` warns when a kept file references a type from an excluded or unmapped package** (#352, closes #292).
  `generate_with_diagnostics` now emits a `CodeGenWarning::ExcludedPackageFieldRef` when a field in a kept file references a type that is neither being generated nor covered by an `extern_path`. The warning precedes the consumer's build, so the dangling `super::…::Type` compile error is accompanied by an actionable diagnostic that names the file, message, and field where the reference appears, the missing package, and the exact `extern_path` or `.files()` fix. Detection is type-granular: references to a specific type from a partially-generated package are correctly flagged even when other types in the same package are being generated.

- **`buffa-build`: `Config::exclude_package` knob** (#383, closes #293). `Config::exclude_package("buf.validate")` (or `.exclude_package(".buf.validate")`) drops all `.proto` files in that package — and any sub-packages — from code generation. Multiple calls accumulate. The same knob is exposed as `exclude_package=<pkg>` in the `protoc-gen-buffa` plugin option string and as `CodeGenConfig::exclude_packages` for direct codegen users. An entry that matches no package in the input now raises `CodeGenWarning::ExcludePackageMatchedNothing` (a `cargo:warning` from `buffa-build`).

- **`protoc-gen-buffa` gains `unbox_oneof=true` and repeatable `unbox_oneof_in=<path>` options** (#392), the plugin equivalents of `buffa_build::Config::unbox_oneof()` / `unbox_oneof_in(&[..])`, opting non-recursive message/group oneof variants into inline storage. Paths are normalized like the other path-scoped options (leading dot optional, whitespace and trailing dots stripped); an empty path is rejected rather than treated as the blanket rule.

- **`buffa-types` ships `google.protobuf.Api`, `Type`, `Enum`, and `SourceContext`** (#394, closes #382). Codegen auto-maps the whole `.google.protobuf` package to `buffa-types`, so compiling googleapis (or any schema importing `api.proto` / `type.proto` / `source_context.proto`) failed with `cannot find type Api` / `TypeView` / `EnumView`. The three files are the rest of the official well-known set; they are vendored at protobuf v33.5 and generated next to `Timestamp`/`Any`, with binary, view, and text codecs and textproto `Any` expansion. They have no `Serialize`/`Deserialize` impls, so a `json = true` message that embeds one of them does not compile; map the type to a locally generated copy with `extern_path` if JSON is needed. One of the new types is `google::protobuf::Option`, which is not re-exported at the crate root: a module that glob-imports `buffa_types::google::protobuf::*` now has it shadowing the prelude `Option`, and `Option<T>` there fails with E0107 — import the types you use by name.

- **`SharedCorpusContext` lets a workspace that generates one crate per proto package pay the corpus-wide codegen analysis once** (#401, closes #400). `generate()` re-derives which oneof variants are unboxed, which message fields are stored inline, and the per-symbol comment map from the whole `FileDescriptorSet` on every call, although none of that depends on the per-package `extern_paths`; a ~2900-package workspace paid that walk 2900 times. Build a `SharedCorpusContext::new(&files, &config)` once and set `CodeGenConfig::shared_corpus_context` on each per-package config; the output is byte-identical, and a context built from a different corpus or different oneof/pointer-repr rules is refused with `CodeGenError::SharedCorpusContextMismatch` rather than silently resolving against the wrong one. The corpus comparison is structural, not by file name, so a regenerated `FileDescriptorSet` with edited content is refused too; it costs `O(corpus)` per call, measured at roughly a quarter of the name-only comparison's saving on that workspace and still well ahead of not sharing. Off by default.

- **`CodeGenConfig::shared_descriptor_pool_root`** (#399): override the computed `super::`-relative path to the shared `__buffa_fds` root in shared-pool mode (`shared_descriptor_pool`) with a caller-supplied path, for workspaces where one crate does not host the whole package tree as nested modules (e.g. one independent Cargo crate per proto package). `None` (the default) keeps the existing `super::`-relative behaviour — purely additive, no change to any existing consumer. Reachable only by direct `buffa-codegen` callers this release; `buffa-build` and the `protoc-gen-buffa*` plugins do not expose it yet.

- **`DynamicMessage::try_from_message`: a fallible, name-resolving bridge from a generated message** (#414, refs #413). Resolves the descriptor from the type's `MessageName` and returns a new `BridgeError` (`MessageNotFound` / `MessageTooLarge` / `Decode`, re-exported from `buffa_descriptor::reflect` and the crate root) instead of panicking when the pool lacks the type or the encoded bytes fail to decode against its descriptor. `DynamicMessage::try_from_message_with_index` is the fallible form for callers that already hold a `MessageIndex`; `from_message` now shares its decode step. The bridge uses the same encoded-length-scaled memory budgets as generated `ReflectMessage::to_dynamic`, so large generated messages avoid false `ElementMemoryLimitExceeded` failures without making the second representation unbounded.

### Changed

- **Two decode-limit documentation claims corrected** (#349). The unknown-field count limit was described as capping overhead at roughly `limit x 40` bytes; that holds for flat input only, and nested groups are now charged separately (see the Fixed entry for #349). And the `Map` hasher docs described the foldhash process-wide seed as mixing ASLR addresses with process start time; that holds on `std`, but `no_std` builds drop the clock and allocator entropy, and on a bare-metal target with no ASLR the seed is a link-time constant, so a colliding key set can be precomputed from the firmware image. These two corrections are documentation-only.

- **`SizeCache` panic locations are now gated on `debug_assertions`, shrinking generated code** (#366).
  Generated `compute_size` calls `SizeCache::set` once per length-delimited sub-message field, and generated `write_to` calls `consume_next` once as well, so a large schema produces hundreds to thousands of call sites for each. Both carried `#[track_caller]`, which materializes a `Location` record at every one of them, and `set` inlined a formatted `assert!` panic block on top of that. The attribute is now gated on `debug_assertions` and `set`'s panic joins `consume_next`'s out of line.
  Measured on a ~1000-message schema linked into a 13.2 MiB binary (fat LTO, `codegen-units = 1`, `panic = "abort"`, stripped): 1068 `Location` records removed, and 106 KiB (0.79%) off the linked binary.
  Both bound checks still run, with the same conditions and messages as before. What changes is that a violation reports a location inside buffa rather than in your `compute_size` / `write_to`. The gate follows the profile buffa itself was compiled with; to get caller locations back in a release build, set `[profile.release.package.buffa] debug-assertions = true` (which also enables buffa's other debug assertions, so treat it as a diagnostic setting).

- **Extension registry lookups by `(extendee, number)` no longer allocate, in either the JSON or the text registry** (#393). Internal representation only; no API, wire, or behaviour change.

- **Same-module AIP-192 rustdoc links are emitted bare** (#394). A `[Mixin][]` reference to a type in the same generated module now renders as `[Mixin]` rather than `[Mixin](crate::…::Mixin)`, which `rustdoc::redundant_explicit_links` rejects under `-D warnings`; cross-module references, fully-qualified display names, and keyword-named types keep the explicit target.

### Fixed

- **A nonempty JSON object for `google.protobuf.Any` without the required `@type` discriminator is now rejected** (#334) instead of silently decoding as an empty message.

- **Generated `decode_view` now applies `DEFAULT_ELEMENT_MEMORY_LIMIT`, matching `Message::decode`** (#338). The view field arms already charged the budget, but the default entry point never attached one, and `register_element_memory` is a no-op without it — so `FooView::decode_view` and `OwnedView::decode` accepted repeated-field payloads that the owned decoder rejects. `DecodeOptions::decode_view` was unaffected. Callers that legitimately decode views of very large repeated fields can raise the ceiling with `DecodeOptions::with_element_memory_limit(n).decode_view(..)`.

- **`google.protobuf.Any` expansion depth is capped at `type_registry::MAX_ANY_EXPANSION_DEPTH`** (100, matching `RECURSION_LIMIT`) in the hand-written `Any` impls in `buffa-types`, for both JSON and textproto (#339). Expanding an `Any` decodes its payload and serializes the result, so an `Any` holding an `Any` recursed once per level with no bound; the decode-time recursion limit cannot see that nesting, because `Any` is a flat two-field message whose chain lives inside its opaque `value` bytes. Past the cap, JSON serialization returns an error and textproto emits the unexpanded `type_url`/`value` form. The reflective `DynamicMessage` JSON codec gained the equivalent bound in #364.

- **`ReflectMessage::to_dynamic` no longer panics on views that decoded successfully** (#341). Two causes: `DynamicMessage` charged two recursion levels for a message-valued map entry where the owned and view decoders each charge one, so a band of nesting depths decoded cleanly as a view and then panicked on conversion (437 bytes of `google.protobuf.Struct` was enough); and the view re-decode applied the fixed untrusted-input limits to bytes the library had just encoded. The map accounting now matches the other two decoders, and the view re-decode scales the element-memory and unknown-field bounds to the encoded length, floored at the defaults.

- **The reflective decoder now charges element memory for packed repeated scalars, packed and unpacked closed-enum elements, and closed-enum-valued map entries** (#342). Generated code exempts packed scalars because a 1-byte varint becomes a 4-byte `i32`; `DynamicMessage` stores each element as a 64-byte `Value` instead, so the same wire bytes bought roughly 64x the memory with the 32 MiB bound attached but never consulted — 4 MB of wire produced 262 MB resident. Consequence for callers: a reflective decode of a large columnar payload (above ~524k packed elements under the default) now returns `ElementMemoryLimitExceeded` where it previously succeeded, and needs `DecodeOptions::with_element_memory_limit` raised.

- **The lazy view family now applies the element-memory budget** (#343). Four gaps composed: generated `decode_lazy` built its context without one, neither the repeated nor the singular message arm charged, and each deferred access rebuilt a context that dropped it — so `DecodeOptions::with_element_memory_limit` had no effect on this family at all. Recording a deferred element or fragment is now charged for the byte-range slot it retains, and the budget remaining at the record site is replayed when the subtree is accessed. Like the recursion and unknown-field limits on this path, the element budget is a per-subtree bound rather than the eager decoder global cap; the rustdoc and guide say so, and the three affected `# Errors` lists now name `ElementMemoryLimitExceeded`.

- **The textproto parser now applies an element-memory budget** (#344). `DecodeContext` never reaches this parser, so repeated and map fields were unbounded there while the identical binary payload was rejected — and the amplification is very nearly as large, an empty repeated element costing three input bytes (`{},`) against two encoded for the same footprint. **This may reject input that parsed in earlier releases**: textproto is a format people hand-write and check in, so a large fixture can now fail with `element memory limit exceeded`. Raise the bound to accept it.

- **An extension field decoded through `MessageCodec` or `GroupCodec` now shares one decode budget across all of its wire records, in either the singular or repeated form** (#345, closes #357). `Message::merge_from_slice` mints fresh budget cells per call, so merging records one at a time gave every record its own full unknown-field and element-memory allowance — turning documented per-decode absolutes into per-record ones, multiplied by however many records the sender chose to send. The carrier sees only opaque records and charges one slot each, so nothing upstream noticed. Reachable from `ExtensionSet::extension` and, with no explicit call, from `serde_json::to_string` on a message carrying a registered extension. New failure mode: an extension whose records together exhaust the budget now reads as absent (or yields a short list), which the getter rustdoc now says. The budget is always the crate default — `ExtensionSet::extension` takes no context, so a `DecodeOptions` used for the carrier does not reach it.

- **The reflective base64 decoder's 32-bit size overflow and the `any_encode_text` debug assertion no longer panic on untrusted input** (#346); on both paths the non-panicking behaviour was already correct. The base64 decoder sized its buffer with `len * 3 / 4`, which overflows `usize` on 32-bit targets (supported, with their own CI job) above ~1.33 GiB of attacker-supplied JSON; it now divides first, which cannot overflow at any length. And `any_encode_text` carried a `debug_assert!` that the stored `Any.value` bytes decode, so a single malformed byte panicked wherever debug assertions are on; that field is a raw `bytes` field that decode never validates, making undecodable content ordinary untrusted input rather than a broken invariant.

- **Reflective map decode is no longer quadratic in the number of wire entries** (#348). `MapValue` is a sorted `Vec` and the binary decode path called its `O(n)` sorted `insert` once per entry — its own doc already said decode paths should batch instead, which the JSON path did and the binary path did not. Entries arriving in descending key order landed at index 0 every time, so a few megabytes of wire turned into minutes of `memmove`. Entries are now appended during the decode and sorted once at the end, including on the error path so a partially-decoded message never escapes with a broken sort invariant.

- **A fully-qualified symbol name is now capped at `MAX_SYMBOL_LEN` (512 bytes, matching protoc)** (#347), which bounds two things in `DescriptorPool` construction — work that happens after decode and that none of the decode budgets cover. Names are built by concatenating the parent name, and every descendant stores its own copy four times over, so a deep prefix is paid once on the wire and once per descendant; a message name is a singular field, so the element budget never charged for it. The cap also bounds nesting: construction walks nested messages recursively in four places with no depth counter, each level adds at least one byte to the name, and the cap is reached in pass 1 before the other three walks run. That closes the unbounded recursion reachable through the public `DescriptorPool::new`, which takes an already-decoded set and so is not covered by the decoder recursion limit. The cap applies to registered symbol names — messages, enums, enum values, services, methods, extensions — not to leaf field or oneof names, whose amplification is linear rather than quadratic.

- **Nested unknown groups now charge element memory for the per-level `Vec` slot each child occupies** (#349). The unknown-field count limit prices a flat field at its ~40-byte `UnknownField`, but a group allocates a `Vec` per nesting level on top of that, and `Vec`'s minimum non-zero capacity is four elements — so a group holding one child costs ~160 bytes against one slot, and a deep chain spent several times what the count implied. The doc on `DEFAULT_UNKNOWN_FIELD_LIMIT` said the count caps overhead at roughly `limit x 40` bytes; that holds for flat input and now says so, with nesting bounded by the two limits together.

- **ProtoJSON parsing for `bytes` extensions now accepts standard and URL-safe base64 with or without padding** (#350), matching ordinary `bytes` fields and the protobuf JSON specification.

- **Replacing a JSON or text extension registry entry now removes the superseded name and number mappings** (#351), keeping serialization and parsing lookups consistent.

- **Reflective `DynamicMessage` JSON integer decoding now matches generated messages** (#353). Quoted decimal and exponent forms parse exactly across the full `i64`/`u64` range (a quoted `"9007199254740993.0"` was previously rejected after a lossy `f64` round trip), and unquoted integer-valued floats above 2^52 - 1 are now rejected, as the generated decoders have done since 0.9.0, because `serde_json` can round such tokens to an adjacent integer before the decoder sees them. Reflective decodes that relied on an unquoted value in that range must quote it. The reflective path now routes through the same `json_helpers` with-modules as generated code, so the two cannot drift apart again.

- **JSON `null` on a registered extension key unsets the extension** (#355), for both singular and repeated extensions. Singular `google.protobuf.Value` and `google.protobuf.NullValue` extensions are the exception: `null` is a present value there. A `NullValue` extension now also serializes as `null` rather than the enum name `"NULL_VALUE"` (`[null, …]` when repeated), matching the reflective codec and ProtoJSON; the parse side accepts `null`, `"NULL_VALUE"`, and `0`. Generated extension registrations reach that behaviour through four new `extension_registry::helpers` functions (`null_value_to_json`, `null_value_from_json`, and their `repeated_` forms), so code generated by this version needs a matching `buffa`.

- **Integer extensions now use the same ProtoJSON decoders as generated fields** (#356). They accept exact quoted decimal and exponent forms across every integer wire type while rejecting unsafe high-magnitude unquoted floats.

- **Strict reflective `Any` JSON decoding now rejects unknown members alongside the `value` of a wrapped well-known type** (#354); `from_json_ignoring_unknown` continues to discard those members.

- **Generated `descriptor_pool()` no longer rejects small schemas built from short type names** (#360, closes #336). The scaled element-memory bound (`len * 64`) could come out tighter than the untrusted-input default it replaced: descriptor sets whose bulk is one-character type names amplify past 64x (the issue's shape measures ~71.5x on 64-bit), so a few-kilobyte schema was rejected even though the flat 32 MiB default before 0.9.1 accepted it. The bound is now floored at `DEFAULT_ELEMENT_MEMORY_LIMIT`, so it can only ever be looser than that default, never tighter.

- **Reflective-package codegen (`ReflectMode::Bridge`/`ReflectMode::VTable`) no longer scales one token per descriptor byte** (#361). The embedded `FILE_DESCRIPTOR_SET_BYTES` constant is now written as a single byte-string literal instead of one token per byte, so its codegen cost no longer scales one token per descriptor byte (which can reach tens of megabytes for a large codegen run). Measured at roughly 20x less build time and 15x less peak memory generating one package against a ~22 MB encoded descriptor set. No change to the constant's type, name, or contents.

- **Reflective ProtoJSON parsing now honours `ignore_unknown_fields` for `google.protobuf.Empty`** (#367), including `Empty` values packed in `google.protobuf.Any`.

- **Generated JSON serialization for message-valued oneof variants now dereferences the configured `ProtoBox` before passing the value to serde** (#372). Custom `ProtoBox` types no longer need to implement `serde::Serialize` just because they are used in a oneof, and the custom-types example now exercises the `ProtoBox` contract without that workaround.

- **Generated `Deserialize` impls reach `core::fmt` through an absolute `::core::` path** (#375). It was the one unqualified path the codegen emitted (on messages with a oneof, or with extension ranges under `preserve_unknown_fields`), so a proto package named `core` produced a module that shadowed the `core` crate and the generated code failed to compile with `E0433: cannot find fmt in core`.

- **`OwnedView::into_bytes` could drop the wrapped view twice if its destructor panicked** (#379, closes #377). The method ran the view's destructor while `self` was still a live `OwnedView`, so a panic inside `V::drop` unwound into `OwnedView`'s own `Drop` impl and dropped the view a second time. Generated view types have no `Drop` impl, so only a hand-written `MessageView` whose destructor can panic was exposed. `OwnedView` now has no `Drop` impl at all: it stores the view before the buffer, in a private `MaybeDangling` wrapper modelled on the `yoke` crate, and relies on declaration-order drop glue, so `into_bytes` is a plain field move and a panicking view destructor cannot be re-entered. The wrapper also hides the view's forged `'static` borrows from the aliasing model, so dropping an `OwnedView` received by value — which Miri reported as undefined behaviour under field retagging — is now well-defined. Reported by HackerOne researcher waynezinn.

- **`merge_bytes` / `merge_string` no longer publish a length before the bytes behind it are written** (#380, closes #378).
  The non-contiguous copy path of `merge_bytes`, `merge_string`, `decode_bytes`, and `decode_string` called `set_len(len)` on the destination and then let `Buf::copy_to_slice` fill it. `chunk()` and `advance()` are safe, user-implementable methods, so a `Buf` that panicked mid-copy (or whose `chunk()` ran dry before `remaining()` said it would) left the caller-owned `Vec<u8>` / `String` with a length covering bytes that were never written — stale or uninitialised heap, and for `String` possibly non-UTF-8 — readable by safe code that caught the unwind. All four sites now copy into the spare capacity chunk by chunk and extend the length only once every byte is in place, so an unwind leaves the merged value empty and a `Buf` that runs dry panics with a message instead of spinning. Not reachable with the stock `bytes` implementations. Reported by HackerOne researcher bezumiya.

- **Generated JSON code uses absolute `::serde` paths** (#384). A proto package or message named `serde` put a `mod serde` in scope that shadowed the crate inside the generated custom message and oneof `Serialize`/`Deserialize` impls, so the generated code failed to compile.

- **`DynamicMessage` equality compares unknown fields by value, in arrival order, rather than by count alone** (#388).

- **`DescriptorPool` rejects field and extension numbers in the implementation-reserved band 19000–19999, as `protoc` does** (#389); only hand-built or synthesized descriptor sets can reach this. The band is named by the new `buffa::encoding::FIRST_RESERVED_FIELD_NUMBER` / `LAST_RESERVED_FIELD_NUMBER` constants and the rejection surfaces as the new `PoolError::ReservedFieldNumber` variant. Extension ranges that span the band load unchanged, matching `protoc` and protobuf-go.

- **ProtoJSON `FieldMask` conversion preserves leading underscores** (#390). A path component such as `_foo` maps to `Foo` and back, matching the C++ and Go implementations; on the parse side a leading uppercase letter, previously rejected as non-canonical, now yields a leading underscore.

- **ProtoJSON `FieldMask` paths are validated the same way on the typed and reflective codecs** (#391). Both now reject a component that is empty or contains a character outside `[a-z0-9_]` (whitespace, `-`, `/`), on parse and on serialize, as C++ and protobuf-go do; previously the reflective parser trimmed whitespace and the typed one kept it. Surrounding whitespace in a path is therefore an error where the reflective codec used to accept `"foo, barBaz"`. `buffa::json_helpers::wkt::field_mask_path_round_trips` carries the new check for anyone calling it directly. The exact path `*` stays accepted as the full-mask wildcard.

- **ProtoJSON `Any` rejects a `@type` whose type name is empty** (#402). `"type.googleapis.com/"` passed the "contains a `/`" check and went on to a registry lookup of the empty name; it is now rejected with the other malformed type URLs.

- **`DescriptorPool` rejects enum values that reuse a reserved name or number** (#405), as `protoc` does. Only hand-built or synthesized descriptor sets can reach this; the rejection is the new `PoolError::ReservedEnumValueName` / `ReservedEnumValueNumber` variants, naming the enum and the value.

- **Textproto accepts a comment between `-` and a special float literal** (#404). The tokenizer already allowed whitespace and comments between the sign and `inf`/`infinity`/`nan`, as the spec and C++ do, but the decoder only trimmed whitespace from the raw span, so `f: - # note\n inf` failed to parse.

- **Generated enums carry `#[allow(non_camel_case_types)]`** (#409, closes #408). The module-tree wrapper emitted by `buffa-build` and `protoc-gen-buffa-packaging` already suppresses the lint, but a per-proto content file consumed on its own (`mod`/`include!` without the packaging plugin) warned on every `SCREAMING_CASE` variant. The attribute is now on each enum, as the scoped `non_snake_case` allow already is on messages.

- **`DescriptorPool` rejects two enum values with the same number unless `allow_alias` is set** (#410), as `protoc` does; with `allow_alias`, lookup by number keeps returning the first declaration. Only hand-built or synthesized descriptor sets can reach this; the rejection is the new `PoolError::DuplicateEnumValueNumber` variant.

- **`DescriptorPool` rejects an open enum whose first declared value is not zero** (#411), as `protoc` does for proto3 and editions `enum_type = OPEN`; closed enums (proto2, or editions `CLOSED`) may still start anywhere. Only hand-built or synthesized descriptor sets can reach this; the rejection is the new `PoolError::OpenEnumFirstValueNotZero` variant.

- **`DescriptorPool` rejects message fields that reuse a reserved name or number, and extension ranges that overlap a reserved range** (#412), as `protoc` does. Only hand-built or synthesized descriptor sets can reach this; the new `PoolError::ReservedMessageFieldName`, `ReservedMessageFieldNumber`, and `ReservedExtensionRange` variants name the message and the offending field or range.

- **`DynamicMessage::from_message`, `to_message`, generated owned-mode `to_dynamic`, and bridge-mode `reflect()` no longer reject large messages the process built itself** (#414, refs #413). Their internal re-decode applied the fixed untrusted-input element-memory and unknown-field budgets to bytes the library had just encoded, so a valid message a few megabytes on the wire panicked with `ElementMemoryLimitExceeded`; the budgets now scale with the encoded length, floored at the defaults, as the generated view conversion already did (#341). The recursion limit and the 2 GiB protobuf size limit still apply.

### Security

- **Reflective JSON serialization (`DynamicMessage::to_json` / `serde_json::to_string(&dyn_msg)`) now bounds nesting across `google.protobuf.Any` payloads** (#364). `DynamicMessage`'s `Serialize` impl decodes `Any.value` at serialize time and previously gave each layer a fresh recursion budget, so a sub-megabyte input of deeply nested `Any` messages — which the binary decoder accepts, since `Any.value` is opaque bytes to it — overflowed the stack (an uncatchable process abort). It now threads one `RECURSION_LIMIT` (100) count through nested messages and `Any` payloads alike, and the inner `Any` decode continues that count rather than restarting it, so over-deep input is a `serde` error (text contains `exceeds buffa::RECURSION_LIMIT`). A `DynamicMessage` whose nesting counted through `Any` exceeds 100 levels now fails to serialize; the cap is not configurable in this release. The generated-code `buffa_types::Any` serializer is covered by #339.

- **View and reflective decoders now merge a repeated message value within one map entry, matching the owned decoder** (#365). For a `map<K, SomeMessage>` field, protobuf merge semantics say that if a single map entry carries its value field more than once, the occurrences merge into one message. The owned decoder did that, but generated `*View` types (including lazy views and `buffa_types::StructView`) and `DynamicMessage` kept only the last occurrence — a parser differential that let a crafted message show different map contents to a view-based check than to owned decoding or JSON transcoding of the same bytes. All decoders now merge. No conforming encoder emits a split value (message concatenation produces separate entries, which are unaffected), so only hand-crafted input decodes differently, and it now decodes the same way everywhere.
